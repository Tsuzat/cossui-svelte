Chat UI is a family of components for conversations in a drawer, a panel, or a page. The components handle presentation and local interaction; your application owns messages, membership, persistence, and authorization.

[Try the complete example](/blocs/view/chat-01): a group chat in a drawer with replies, reactions, pinning, receipts, mentions, and conversation states. All examples use synthetic conversation data.

## Start here

- **Build a conversation:** install `chat` with `composer` and `avatar`, then use the [minimal example](#minimal-conversation).
- **Adapt the full drawer:** open the [`chat-01` bloc](/blocs/view/chat-01) and copy its source, then read the [source map](#source-map) and [application responsibilities](#connect-your-application).
- **Working as an agent:** the [chat registry source](/r/chat.json) includes file contents and dependencies. Use the exported TypeScript props as the API contract; the live example alone does not expose the implementation.

## Install

Configure the project using [Get started](/docs/get-started), then install the family:

```bash
npx shadcn-svelte@latest add https://cossui-svelte.com/r/chat.json
```

This installs the chat source into your components directory under `ui/chat/`, including its scroll controller and text helpers. It also installs the required coss components, Lucide icons, and ShardsUI. Keep Tailwind source scanning enabled for the installed directory.

The complete drawer example is a [bloc](/blocs/view/chat-01), separate from the component family. Its roles, moderation decisions, timers, and receipt aggregation are sample application code. Adapt them to your product's rules.

## Minimal conversation

The example also uses Composer and Avatar. Install them explicitly alongside the chat family:

```bash
npx shadcn-svelte@latest add https://cossui-svelte.com/r/chat.json https://cossui-svelte.com/r/composer.json https://cossui-svelte.com/r/avatar.json
```

This complete component demonstrates plain-text sending with local state. A conversation needs a bounded height, a scroll controller, messages, and a draft. Use the full drawer example for mentions, grouped messages, reactions, and focused replies.

```svelte
<script lang="ts">
  import ArrowUp from '@lucide/svelte/icons/arrow-up';
  import { MediaQuery } from 'svelte/reactivity';
  import { Avatar, AvatarFallback } from '#lib/components/ui/avatar';
  import { ChatConversation, ChatMessage, ChatScroll } from '#lib/components/ui/chat';
  import {
    Composer,
    ComposerActionGroup,
    ComposerActions,
    ComposerInput,
    ComposerSubmit,
    type ComposerValue,
    getComposerText
  } from '#lib/components/ui/composer';

  const hintId = $props.id();
  const touchInput = new MediaQuery('(pointer: coarse)');

  let draft = $state<ComposerValue>([]);
  let messages = $state([
    {
      id: 0,
      own: false,
      text: 'The same chat components can live directly in a page. Try sending a message.'
    }
  ]);

  const scroll = new ChatScroll(() => ({ itemCount: messages.length }));
</script>

<section aria-label="Inline chat example" class="flex h-96 flex-col rounded-xl border bg-popover">
  <ChatConversation {scroll} label="Inline conversation" jumpLabel="Jump to latest">
    <div class="space-y-4 pt-4">
      {#each messages as message (message.id)}
        <ChatMessage
          side={message.own ? 'outgoing' : 'incoming'}
          author="Casey"
          animateEntrance={message.own}
        >
          {#snippet avatar()}
            <Avatar aria-hidden="true" class="size-7 text-xs">
              <AvatarFallback>C</AvatarFallback>
            </Avatar>
          {/snippet}
          {message.text}
        </ChatMessage>
      {/each}
    </div>
  </ChatConversation>
  <div class="flex shrink-0 flex-col gap-2.5 px-4 pb-4">
    <Composer
      bind:value={draft}
      submitOnEnter="desktop"
      onSubmit={(value) => {
        const text = getComposerText(value).trim();
        if (!text) return;
        scroll.atBottom = true;
        messages.push({ id: messages.length, own: true, text });
        draft = [];
      }}
    >
      <ComposerInput
        as="textarea"
        aria-describedby={touchInput.current ? undefined : hintId}
        aria-label="Inline message"
        placeholder="Write a message…"
      />
      <ComposerActions>
        <ComposerActionGroup align="end">
          <ComposerSubmit aria-label="Send message" size="icon">
            <ArrowUp aria-hidden="true" />
          </ComposerSubmit>
        </ComposerActionGroup>
      </ComposerActions>
    </Composer>
    {#if !touchInput.current}
      <p id={hintId} class="text-end text-muted-foreground text-xs">
        Enter to send / Shift + Enter for a new line
      </p>
    {/if}
  </div>
</section>
```

In a real application, `onSubmit` starts your mutation. Clear the draft after accepting the message into your local send queue. Give each message a stable client ID so replacing a pending message with the server response does not remount it.

## Component map

Import everything from the `chat` module. There is no required global chat provider.

| Area | Components | Responsibility |
| --- | --- | --- |
| Conversation | `ChatConversation`, `ChatScroll` | Scroll viewport, end following, jump to latest, overlay slot |
| Message | `ChatMessage` | Incoming/outgoing row, avatar, author, grouping, actions, reactions, footer |
| Surfaces | `ChatMessageBubble`, `ChatBubble`, `ChatMessageLayout` | Standalone previews and custom row compositions |
| Content | `ChatMessageText`, `ChatCollapsibleMessage`, `ChatReplyReference` | Mention emphasis, long text, quoted message navigation |

| Actions | `ChatMessageActionToolbar`, `ChatReactionPicker`, `ChatReactionChip` | Reply/menu controls, emoji selection, reactor list |
| Focused reply | `ChatReplyPreview` | Move the selected message above the composer, dim the timeline, cancel/exit |

| Activity | `ChatTypingIndicator`, `ChatDeliveryIndicator` | Typing and delivery presentation |
| People | `ChatMemberList`, `ChatMemberSection`, `ChatMessageInfo` | Member rows and receipt groups with supplied actions |
| States | `ChatEmptyState`, `ChatLoadingState`, `ChatStatusBar` | Joining, unavailable history, loading, connection feedback |

## Messages and actions

`ChatMessage` requires `side` and `children`. It accepts `author` and an `avatar` snippet, plus `actions`, `reactions`, and `footer` snippets. Set `grouped` for consecutive messages from the same sender; it hides repeated incoming authors/avatars while preserving the avatar column. The first bubble uses a smaller upper corner on its sender's side; grouped bubbles use equal corners. Bind the bubble element with `bind:bubbleRef`, and pass native attributes through `bubbleProps`.

Grouping and vertical spacing belong to the composition. The drawer breaks groups at date changes and deleted messages. It uses `pt-5` between senders, `pt-1` within a group, and `pt-3` after a grouped message with delivery metadata. Omit that padding immediately after a date or unread separator. Show incoming timestamps at the end of a group; outgoing delivery feedback remains per message. `ChatDeliveryIndicator` exposes a labelled image rather than a live region. Announce important send failures through a single application-owned status region.

String children render through `ChatMessageText`. For mention emphasis, render `ChatMessageText` with `mentions` containing known handles. Custom snippet content passes through unchanged.

`ChatCollapsibleMessage` requires `text`, `side`, `showMoreLabel`, and `showLessLabel`. Its default `maxPreviewLength` is 500; shorter text has no expansion control. Use the `renderText` snippet to preserve mention formatting in both views. Choose uncontrolled `defaultOpen` or a bound `open`, and keep that choice stable. Keep images and attachments outside this text-only component.

Use `bubble={false}` for a deleted-message placeholder. Your application decides whether historical messages remain after membership changes.

The toolbar reserves its width beside the bubble and appears on hover, keyboard focus, or coarse pointers. Popups dismiss on user scroll input in their scroll container. Automatic scrolling as messages arrive does not dismiss them.

### Reactions

`ChatReactionPicker` takes `options` (`{ emoji, label }[]`), `selectedEmojis`, `onSelect`, and the accessible strings `triggerLabel`, `triggerTooltip`, and `popupLabel`. When composing it through the `reactionPicker` snippet of `ChatMessageActionToolbar`, pass the snippet's toolbar element to `popupAnchor`.

| Surface | Incoming message | Outgoing message |
| --- | --- | --- |
| Picker anchored to the toolbar | `popupAlign="end"` | `popupAlign="start"` |
| Reactor popup anchored to its chip | `popupAlign="start"` | `popupAlign="end"` |

`ChatReactionChip` is controlled through `selected`, `count`, and `onclick`; it does not update your reaction data. Supply `emoji` and an accessible `label` describing the action and count. Clicking or pressing Enter/Space toggles the reaction. With a `reactorContent` snippet, delayed hover, keyboard focus, or a long touch opens the list; also provide `reactorLabel`. The caller renders names, avatars, and a "You" marker, with a bounded scroll area for long lists. Set `animateEntrance` only for newly added chips.

## Composer and mentions

Use the shared [Composer](/docs/composer) with a bound `ComposerValue` and `onSubmit`. Convert accepted drafts with `getComposerText(value).trim()` and clear them with `[]`. The minimal example uses `<ComposerInput as="textarea" />` for plain text. Mentions require the default contenteditable input.

The drawer uses `layout="adaptive"` and sets these variables on `Composer`:

| Viewport | Minimum rows | Maximum rows |
| --- | --- | --- |
| Below `md` | `--composer-min-rows: 1` | `--composer-max-rows: 4` |
| `md` and wider | `--composer-min-rows: 2` | `--composer-max-rows: 6` |

These are chat composition choices, not the Composer defaults. The draft scrolls after reaching its maximum; keep the action row outside that scroll area. The drawer's send button is round. If adding its tooltip, anchor a `TooltipPopup` to the `ComposerSubmit` element so the submit control retains its disabled behavior. Empty drafts disable `ComposerSubmit` automatically.

Set `submitOnEnter="desktop"` so touch Return inserts a newline. Keep the keyboard hint hidden for coarse pointers. `disabled` blocks editing and sending; the drawer also dims the field and hint. Opening the drawer preserves its default focus and does not open the software keyboard.

For mentions, pass an `@` trigger containing stable member IDs and handle labels. Compose `ComposerPopup`, `ComposerList`, and `ComposerItem` to display each member's avatar and full name. The shared editor handles keyboard selection, token insertion, IME input, and empty matches. Keep the structured draft until submission; a displayed mention is not authorization.

## Scrolling and replies

Create one `ChatScroll` and pass it to `ChatConversation`. Its options are a function, so they stay reactive: update `itemCount` when messages change and `layoutKey` for other size changes such as a typing row. Set `active` to the drawer's open state. Set `paused` while a nested drawer or focused reply owns the interaction.

End following runs only while the reader is at the bottom. Set `scroll.atBottom = true` before appending a locally sent message. Incoming messages should preserve a reader's position when they are reviewing history. The controller does not fetch, paginate, virtualize, or compensate for prepended history; preserve the visible anchor in your data integration. Use `resetScroll()` when changing rooms, not on every message update. `onReachEnd` reports scrolling near the bottom, not proof that a recipient read each message.

`ChatConversation` supplies a labeled `role="log"`. Set `live="off"` if your application announces new arrivals separately, particularly when inserting older history.

`ChatReplyReference` delegates quote navigation to the caller through `onclick`: locate the source, scroll it into view, focus a labeled message container with `tabindex="-1"`, then apply `highlighted` after scrolling settles. Cancel pending navigation when another quote or reply is selected.

For focused replies, read `chat-demo.svelte`, `chat-demo-message.svelte`, and `chat-demo-reply-focus.svelte` together:

1. Measure the bubble through `bind:bubbleRef`. `ChatReplyTarget` contains its DOM element (`source`), measured `width`, and `firstInGroup`. Snapshot the long-message expansion state too.
2. Render `ChatReplyPreview` inside the conversation's `overlay` snippet. Supply the message content, author, reply/cancel labels, `onCancel`, and a `dismissalRef` containing `"cancel"` or `"send"`.
3. Pause the scroll controller, set the conversation `inactive`, and keep the source mounted with `lifted`. Focus the composer for the explicit reply action.
4. Set the dismissal reason before removing the preview. Cancel returns it to the source; send dismisses it. Retain the measured target and paused/inactive state until the exit transition finishes, then clear them. Preserve the source's expansion state when cancelling.

## Drawer and mobile keyboard

Compose the chat inside the regular coss [Drawer](/docs/drawer). Keep its header, conversation, and composer as separate flex children. The conversation needs `min-h-0` and a bounded available height.

The example uses a right inset drawer on larger screens and a bottom drawer below `md`. The bottom `DrawerPopup` already handles the software keyboard; do not add another provider. Keep `[--drawer-height:100dvh]`, keyboard/safe-area bottom padding, and the portal viewport's mobile `pt-2` together. The composer becomes a single-row field with a bounded scroll area on narrow screens.

Keep the drawer's default initial focus. Focus the composer only after an explicit reply, join, rejoin, or successful reconnect. Nested members and message-info drawers return focus to their trigger. Preserve the default modal behavior so the page cannot scroll behind an open drawer.

## State and moderation examples

The drawer combines conversation states with membership and message actions. Its default conversation has no pin; select **Pinned message** to try it. **First message** begins with a join introduction and opens an empty conversation with a composer after joining.

| State | Timeline and composer | Recovery |
| --- | --- | --- |
| Not joined | Join introduction; no history or composer | Join after eligibility succeeds |
| Joined, empty | Empty conversation with composer | Send the first message |
| Loading | Skeleton and disabled composer | Wait for history |
| Disconnected | Cached history and disabled composer | Reconnect with pending feedback |
| History error | Empty state; no composer | Retry history |
| Access lost | Empty state; no history or composer | No automatic restoration |
| Removed | Empty state; no history or composer | Eligible explicit rejoin |
| Banned | Empty state; no history or composer | No rejoin while banned |
| Left | Empty state; no history or composer | Eligible explicit rejoin |

These are isolated previews, not a state-precedence resolver. In your integration, access denial takes precedence over cached history, a ban over rejoin, and mute over enabling send after reconnect. The muted member's own view is not demonstrated; implement readable history with sending and typing disabled if your product supports mute.

The drawer demonstrates confirmation before leaving, removal, banning, and deletion. Its role rules and rejoin/unban behavior are sample application policy. Deleting a message replaces its body, clears reactions and any pin, and updates quoted previews. Keep those surfaces consistent when applying server events.

Message info uses a nested drawer with the same outgoing message content and mutually exclusive Read by, Delivered to, and Pending delivery groups. Returning from nested drawers preserves the draft and reading position.

## Animation

Message and reaction-chip entrance animations are opt-in through `animateEntrance`; enable them for new arrivals rather than loaded history. Use `highlighted` to draw attention to a quoted message. Chat animations respect `prefers-reduced-motion`.

## Connect your application

1. **Map data:** stable message IDs, sender IDs, display names, timestamps, grouping, and attachment content.
2. **Own delivery:** track sending, sent, delivered, read, and failed states from your transport. Pass the derived state to `ChatDeliveryIndicator`. Successful retries must replace stale recipient receipts as well as the aggregate status.
3. **Own mutations:** wire send, retry, react, reply, pin, delete, and membership actions to your server. Preserve drafts on failures.
4. **Authorize on the server:** the demo's host/co-host/guest rules are examples. Hide unavailable UI actions and recheck every mutation server-side.
5. **Define access:** distinguish leaving/removal from bans according to your product. The example permits rejoining after removal, blocks rejoining while banned, and restores membership on unban. These are deliberate demo choices, not component-enforced rules.
6. **Handle subscriptions:** remove listeners and pending operations when the room changes. Do not send or emit typing while muted or without access.
7. **Supply copy:** localize component labels, descriptions, timestamps, and empty-state content in your application.

## Before shipping

Check keyboard-only operation, IME input, mentions in reply mode, reduced motion, long drafts, narrow layouts, and a real mobile virtual keyboard. Test send/retry failures, removed reply targets, duplicate delivery events, reconnect, and history pagination with your own backend. The example uses local state and timers; it does not persist or transmit messages.
